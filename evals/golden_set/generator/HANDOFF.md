# 온토메틱 생산 문서 세트 — 인수인계 (최소판)

## 현재 실행 방법 Python 전환

저장소 루트에서 Python 3.12와 기존 `uv` 환경만 사용한다. Node.js·npm·Bun은 필요 없다.
현재 데이터는 4개 모델 각각 문서 10개, 정답 11개, 오류 사례 26개다.
아래의 이전 기록에 나오는 JavaScript·TypeScript 명령과 옛 폴더명은 사용하지 않는다.

```sh
uv run python -m evals.golden_set.extractor.eval
uv run python -m evals.golden_set.extractor.check_wrong
uv run python evals/golden_set/generator/make_golden.py --check
uv run python scripts/check.py
```

평가는 기존 데이터를 읽고 `evals/golden_set/reports/`에 보고서를 쓴다.
DOCX 해석은 `backend.parsers.documents.docx.parse_docx`를 재사용한다.
`extractor/parser.py`는 `ParsedDocument`의 텍스트·표와 `TextBlock.heading_level`을 평가용 블록으로 변환한다.
회귀 평가는 설정에 따른 외부 API 호출 없이 backend의 로컬 DOCX 파서를 직접 사용한다.
불일치·중복·초과 추출, 빈 평가, 오류 미검출, 원본의 규칙 위반은 종료 코드 1로 처리한다.
사람이 검수하지 않은 정답의 `draft` 상태는 유지한다. 현재 평가기는 양식 기반 회귀용이며 운영 LLM 평가가 아니다.
추가된 Langfuse 추적은 `--langfuse`를 명시할 때만 켜며, 기본 실행은 로컬 평가다.

```sh
# 기존 데이터를 덮어쓰지 않고 별도 출력으로 생성한다.
uv run python -m evals.golden_set.generator.build_cgs evals/golden_set/reports/d100.docx evals/golden_set/generator/d100.json
uv run python -m evals.golden_set.generator.build_cgs evals/golden_set/reports/d100_split evals/golden_set/generator/d100.json --split
uv run python evals/golden_set/generator/check_cgs.py evals/golden_set/reports/d100.docx evals/golden_set/generator/d100.json
uv run python evals/golden_set/generator/make_wrong_set.py --output evals/golden_set/reports/wrong_set
uv run python evals/golden_set/generator/make_review.py
```

문서·오답 생성은 기존 출력 경로를 거절하고, 새 경로에 생성이 끝난 뒤 공개한다.
정답 생성의 `--check`는 읽기 전용이다. 동일한 정답은 재기록하지 않으며 값 변경 시 `--force`가 필요하다.
문서 생성과 정답 생성은 모델 데이터 구성 규칙을 공유하고 추출기와는 분리되어 있다.
생성 문서의 내용은 기존 정답으로 검증하며, 과거 JavaScript 생성기의 페이지 배치를 그대로 복제하지 않는다.

이하 내용은 전환 전 작업 기록이다.

회사가 준 사양서·생산일정 엑셀로, 제품 한 대가 설계 → 완성(최종 결합·검사)까지 거치는 문서 한 세트를 만든다. **한 회사(온토메틱)가 만드는 4개 모델 모두 완료**(2026-11-02): LO-D100 디지털 11종, LO-T400 초망원 11종, LO-F35 필름 11종, LO-I100 즉석 10종 = 43개 파일. I100은 2차 모듈 렌즈 공정이 엑셀에 없어 '작업 순서 (렌즈 공정)'이 없다.

## 문서 만드는 작업 수정 (2026-11-03, 코드만 반영 · docx는 "make docs" 전까지 다시 만들지 않음)

사용자 요청 5가지를 `build_cgs.js`·`cgs_models.json`·`check_cgs.py`에 반영했고, 임시 폴더에서 4개 모델 모두 합본 빌드 + 검사 27/27 통과, D100 `--split` 10개 파일 생성까지 확인했다. `docs/data/` 의 docx·골든·대조표·오답 세트는 **아직 예전 구조(11종)** 그대로다.

- **생산계획서**: '생산계획' 표의 비고 열 삭제. '작업 일정' 표에서 공정-01(구매 부품 입고·수입검사, 품질부서 일)을 빼고, 다른 공정의 선행 작업에서도 뺌. 공정번호 자체(공정-01)는 수입검사성적서에 그대로 남음. 시작일 계산은 공정-01 종료일을 계속 따른다(표에만 안 보임).
- **투입 → 산출 표기**: '광학 공정' 같은 공정 이름을 쓰지 않고 일정표 그대로 '광학부·경통부 …'(만들어지는 것). 공정 이름만 '광학 조립'. (`renIO`/`ren_io` 삭제)
- **작업 순서 문서**: 2차 모듈(렌즈·본체)을 한 문서(`작업 순서 (2차 모듈)`)로 합침 → 문서는 **4개 모델 모두 10종**(사양서, BOM, 수입검사, 생산계획, 작업 순서 1차/2차/완제품 3, 검사성적서 3). 완제품 문서 이름은 `작업 순서 (완제품 공정)` 그대로.
- **렌즈·본체·완제품 공정 세부 단계**: 일정표에 작업이 하나뿐이라 한 공정번호 안을 실제 조립 순서로 나눔(`cgs_models.json` 모델별 `steps`, 행 = [단계 이름, 작업 내용, 투입, 산출, 확인 내용]). D100·T400 렌즈 6·본체 8·완제품 6단계, F35 렌즈 6·본체 6·완제품 6, I100 본체 6·완제품 5(렌즈 공정 없음). 첫 단계 투입 = 일정표 투입, 마지막 단계 산출 = 일정표 산출을 빌드가 검사한다. 확인 내용(MTF, 센서 정렬 …, 최종 검사)은 마지막 단계에 한 번. 일정·인원·생산 기록·검사는 공정번호 단위 그대로.
- `check_cgs.py`: 2차 모듈 한 문서, 비고 열 없음, 공정-01 없는 일정, 세부 단계 검사로 교체.

## 4개 모델 일반화 (2026-11-02)

- 모델별 값은 `cgs_models.json` 하나에 있고 `build_cgs.js`·`check_cgs.py`가 같이 읽는다: `items`(품목·공정번호·한 줄로 묶는 `merge`), `check`(확인 내용), `ins`(검사 항목), `qty`·`qty_note`(대당 수량과 근거), `rec`(생산 실적), `crew`·`owner`·`assist`(인원·이름), `checklist`(완제품 점검표, `{나사}` `{와셔}` `{MODEL}` `{LENS}` 치환). D100 값은 예전 코드 값 그대로.
- 회사 전체가 함께 쓰는 값: 조직 12명(`PEOPLE`), 공정책임자 3명(`leaders`), 공급사(`SUPPLIER`), 수입검사 확인 내용(`IQC_CHECK`, 나사 규격·스트랩 치수는 BOM에서 읽음). 작업자는 제품 라인마다 다른 사람(T400 26명, F35 23명, I100 18명, 4개 라인 이름이 서로 겹치지 않음, [가상]).
- 공정번호: 포장 라인(부속품 키팅, 포장·출하)을 이름으로 빼고 남은 공정을 엑셀 순서대로 이어 매긴다(D100 17 → 공정-16, F35 15 → 공정-14, I100 11 → 공정-10).
- 시작일: 4개 모델 모두 엑셀 시작일보다 3근무일 앞당긴다(`extract_cgs.py ... auto`). D100 10-28, T400 11-04, F35 11-11, I100 11-18. 양산 이관일 = 시작 전 근무일, 사양서 발행일 = 그보다 2근무일 앞.
- 표지에 '회사 제품' 표(4개 모델의 수량·시작·완성일)를 넣었다.
- 생산 실적(T400·F35·I100)은 D100의 공정별 불량 수를 생산 수량에 비례해 반올림한 [가상] 값. 투입 = 선행 양품의 최소값.
- 결재 규칙 보완: T400·F35는 렌즈 갈래가 늦게 끝나 2차 모듈 공정(본체 또는 렌즈)이 1차 모듈 검사성적서 결재(단계 마지막 공정 종료일) 전에 시작한다. 엑셀 일정상 피할 수 없어서, 검사는 "다음 공정은 들어오는 공정이 끝나 검사 판정을 마친 뒤 시작"으로 보고, 결재 전에 시작하는 공정은 작성 근거에 적는다(`earlyNote`).
- 파일: `node build_cgs.js <폴더> <json> --split`이 문서마다 파일 하나를 만든다(표지·부록 없음, 이름은 `01_제품사양서.docx`처럼 흐름 순서 번호 + 문서 이름). `--split` 없이 주면 예전처럼 표지·부록이 있는 합본 하나. 검사 스크립트는 합본을 읽으므로, 합본을 만들어 검사한 뒤 같은 코드로 나눈다.

## D100 결과 (11종, 쪽 수는 다시 만들어 확인 필요)

제품사양서 / BOM 및 양산 이관(관문 1) / **작업 순서 4개(1차 모듈 6개 품목은 한 문서, 렌즈·본체·완제품은 각각 한 문서)** / 수입검사성적서(구매 14종, 관문 2) / 생산계획·작업지시서(작업자 배정 포함, 품목 9줄) / 검사성적서 3개(1차 모듈·2차 모듈·완제품 단계별, 관문 3).

- 구조: 부품 22 → 1차 모듈 7 → 2차 모듈(렌즈·본체) + 부속품 → 완제품. 공정번호(문서에는 '공정-01 ~ 공정-16'. 엑셀 D100-01~15는 같은 번호, D100-17 → 공정-16, 포장 라인 D100-16·18은 뺌)가 문서를 이어 준다.
- 작업 순서 문서는 `순서-05`(1차 모듈: 광학·경통·센서·셔터·화면·전원·외장 6개 공정(화면·전원은 한 표)을 '■ 광학 공정' 같은 소제목 아래 표로 나눔), 렌즈, 본체, 완제품 4개. 그 품목에 들어가는 부품 가공 공정은 품목 표 맨 앞(예: 렌즈 가공 → 광학 공정 표). 품목마다 작업지시 번호와 묶음 번호(OPT-1028 등)는 그대로 따로 있고, 작업지시서의 '작업 순서' 열은 1차 모듈 품목 모두 `OPS-…-M1`. 코드의 `ITEMS`·`ROUTE_DOCS`에 정의.
- 검사성적서는 단계별 3개이고 안에서 품목마다 소제목("■ 광학 공정", 지시·묶음 번호는 생산계획 표에만)과 생산 기록·검사 결과를 둔다. 검사가 없는 품목은 생산 수량만 적는다.
- 화면부(공정-12)와 전원부(공정-13)는 선행 작업·기간·라인이 같고 검사가 없어 한 문서·한 줄로 묶었다(공정번호는 둘 다 표시).
- 완제품 검사성적서 안 "묶음 연결" 표가 반제품 묶음 → 모듈 묶음 → 완제품 묶음을 잇는다.
- 일정: 완성일 2026-11-12(공정-16 최종 결합·검사 종료일). 포장 라인(부속품 키팅·포장·출하)은 사용자 요청으로 다루지 않는다(2026-11-01). 문서 본문에 '발표일'·'출하'라고 쓰지 않는다.
- 작업자 29명(공정책임자 이서준=1차 모듈, 김민준=2차 모듈, 박도윤=완제품 + 담당·보조 26명). 공정마다 인원 = 책임자 1 + 담당자 1 + 보조담당자(나머지, 이름을 모두 적음). 인원 2명 공정은 보조 없음("—"). 이름은 사용자가 위임한 랜덤 배치 결과를 `build_cgs.js`의 `OWNER`·`ASSIST`에 고정했고 같은 사람을 두 공정에 겹치지 않는다.
- 표지 "확인된 근거와 한계"는 부록 맨 앞으로 옮김(표지가 한 쪽에 들어가게).

## 확정된 방침 (바꾸지 말 것)

- 회사 이름은 **온토메틱**(사용자가 여러 번 바꿈. 2026-11-03부터 온토메틱만 쓴다). 모델 코드(LO-xxx)는 자료 그대로.
- 생산계획·작업지시서에는 '작업지시' 표를 따로 두지 않는다. 작업지시 번호·묶음 번호는 생산계획 표의 열이다.
- 수입검사성적서 표는 부품·확인 내용·판정 3열이고, 확인 내용은 부품 재질에 맞춰 부품마다 다르게 적는다(`IQC_CHECK`, [가상]).
- 값 표시: [자료] 회사 자료 / [가상] 자료에 없어 우리가 채움 / [설계] 우리가 정한 구조. 부록에 모아 둠.
- 제목만 쓰고 제목 아래 한 줄 설명(소제목)은 없다(사용자 요청). 서명 칸은 R&D부서·생산부서·품질부서.
- 작업 순서는 공정 번호 대신 순서 1, 2, 3과 공정번호. 작업자는 번호가 아니라 이름.
- BOM 표는 부품 22줄만, 열은 순번·품목코드·품목명·수량·조달·공급 (구분·분류 태그·모듈 줄·완제품 줄 없음, 맨 앞 열은 1~22 순번). 양산이관서는 BOM 문서 안에 합침(개정이력 없음), 부적합보고서·작업실적은 별도 문서 없음(작업실적은 검사성적서에 합침, 불량은 한 줄).
- 수입검사는 **구매 부품만** 한 장에 합격/불합격. 자체 가공 부품은 '부품 준비' 공정에서 만든다.
- 문서는 사용자가 "make docs"라고 말하기 전에는 만들지 않는다. 커밋은 요청 전까지 하지 않는다.

## 코드에는 반영, 문서(docx)는 "make docs" 전까지 다시 만들지 않음 (모두 사용자 승인)
- 구매 부품 공급사 이름 "㈜가상○○" → "㈜한국○○" (`SUPPLIER`). 이름은 [가상] 표시 유지. BOM·사양서에는 '포장'이라는 말을 쓰지 않는다: 제품 라벨·로고 플레이트 ㈜한국인쇄, 스트랩 ㈜한국섬유, 사양서 부속품 소제목은 '부속품 사양'. 부속품(렌즈 캡·스트랩)은 BOM에 그대로 둔다(2026-11-01, docx에는 다음 make docs 때 반영).
- 머리 칸 용어: 개정 Rev A → "버전 1.0"(제품사양서만 원본 번호 "2.0"), 기준 BOM → "근거 부품표", 시행일·작성일·기준일 → "발행일", 작업ID → "공정번호". 표지에 "머리 칸 읽는 법" 4줄(버전·근거 부품표·발행일·공정번호)과 문서번호 한 줄 설명.
- 번호는 모두 한글 `종류-순번`. 문서번호의 숫자는 표지의 문서 흐름 순서와 같다: 사양-01, 부품표-02, 수입검사-03, 계획-04, 순서-05(1차 모듈), 검사-06(1차), 순서-07(렌즈), 순서-08(본체), 검사-09(2차), 순서-10(완제품), 검사-11(완제품). 작업지시 `지시-01~09`는 공정 순서대로(광학 01, 경통 02, 센서 03, 셔터 04, 화면·전원 05, 외장 06, 렌즈 07, 본체 08, 완제품 09), BOM 품목코드는 `부품-01~22`(순번과 같음). 공정번호는 json을 읽을 때 D100-NN → 공정-NN으로 바꾼다(`build_cgs.js`·`check_cgs.py` 둘 다). 모델명은 회사 자료 그대로 LO-D100(사용자 요청으로 한글화하지 않음). 제품번호는 `모델명-순번 세 자리`(LO-D100-001 = 첫 번째 대, `SERIAL`). docx 파일 이름은 `온토메틱_LO-D100_문서11종.docx`. 번호 정의는 `build_cgs.js`의 `DOCNO`와 `check_cgs.py`의 `NO`.
- 품목 이름을 "~ 공정"으로: 광학 공정, 경통 공정, 센서 공정, 셔터 공정, 화면·전원 공정, 외장 공정, 렌즈 공정, 본체 공정, 완제품 공정(`ITEMS`의 name). 생산계획의 완제품 줄은 "LO-D100 카메라" 그대로. 일정표(엑셀) 값인 공정 이름("광학부 조립")과 투입→산출("광학부")은 [자료]라 그대로 두었다 — 검사 스크립트가 엑셀과 같은지 본다.
- 문서 순서를 공정 흐름대로: 사양서 → BOM → 수입검사 → 생산계획·작업지시서 → 작업 순서(1차 모듈) → 검사성적서(1차) → 작업 순서(렌즈 공정) → 작업 순서(본체 공정) → 검사성적서(2차) → 작업 순서(완제품 공정) → 검사성적서(완제품). `check_cgs.py`가 순서도 확인한다.
- 작업 순서 문서 소제목에서 "(순서 1부터 차례로)" 삭제, 괄호 설명 삭제(BOM "구성", 작업 순서 확인 내용 "광축 중심"·"MTF", 검사성적서 설명 문단).
