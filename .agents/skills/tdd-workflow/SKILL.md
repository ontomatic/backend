# Backend TDD 작업 절차

Backend의 새 동작과 버그 수정은 **Red → Green → Refactor** 순서로 진행한다.
Git 준비·요구사항 문답·브랜치 생성은 [start-task-workflow](../start-task-workflow/SKILL.md), 공통 규칙과 검증·인계는 [작업별 절차](../../workflows.md)를 따른다.
이미 준비한 브랜치와 같은 작업의 진행 상태를 이어가며 Git 준비를 반복하지 않는다.

각 단계 직전에 변경 대상·동작·영향·검증·완료 기준을 설명하고 사용자의 이해와 **해당 단계의 명확한 반영 승인**을 확인한다.
이 승인은 기존 작업 시작 절차의 단계별 승인을 충족하므로 같은 단계의 승인을 이중으로 요구하지 않는다.
전체 계획에 대한 동의, 단순 질문·설명 요청이나 이전 단계의 승인을 다음 단계의 승인으로 간주하지 않는다.
승인 범위가 달라지면 다시 설명하고 확인받으며, 같은 범위의 실패 수정과 재검증은 현재 단계 안에서 수행한다.

## 동작과 필요한 테스트 선정

1. 관련 코드·기존 테스트를 읽고 동작 단위로 입력, 기대 결과, 의미 있는 경계 조건과 완료 기준을 합의한다.
2. 수정 전에 저장소 루트에서 `uv run python scripts/check.py`를 실행해 기준 결과를 확인한다. 기존 실패와 새 실패를 구분하고 요청 범위 밖의 실패를 임의로 수정하지 않는다.
3. 기존 테스트가 요구사항을 충분히 검증하면 재사용한다. 추가가 필요하면 검증할 동작과 기존 테스트로 부족한 이유를 설명하고 최소한의 사례를 선정한다.
4. `uv run python -m pytest`에 대상 파일이나 node ID를 지정해 단계별로 실행할 명령과 영향 범위의 테스트를 정한다.

새 동작, 버그 재현, 의미 있는 경계 조건과 회귀 위험을 검증하는 테스트만 추가한다.
개수·커버리지 수치를 채우기 위한 사례, 같은 의미의 중복 사례, 구현을 그대로 따라 쓰는 검증은 추가하지 않는다.
내부 호출 순서·횟수는 외부 계약에 필요한 경우에만 검증한다. 불필요한 테스트를 만들기 위해 Red를 강제하지 않는다.

## Given–When–Then 작성

새로 작성하거나 수정하는 **각 테스트**는 pytest를 그대로 사용하며 주석과 코드 구조로 다음 역할을 구분한다.

- **Given:** 입력, 사전 상태, fixture와 의존성 준비.
- **When:** 검증하려는 동작 실행.
- **Then:** 관찰 가능한 결과·상태 변화·예외 검증.

fixture·매개변수화를 활용하되 각 테스트에서 준비 조건과 검증 의도가 드러나게 한다.
예외 검증처럼 실행과 검증이 결합되는 경우에도 역할을 명확히 표현하고 형식만 맞추기 위한 불필요한 assertion을 추가하지 않는다.
기존 테스트 전체를 형식 통일 목적으로 일괄 수정하지 않는다.

## Red: 필요한 테스트로 실패 확인

Red에서 작성할 테스트, 기대하는 실패와 필요한 골격을 설명하고 **Red 승인을 받은 뒤** 수정한다.
승인 범위는 필요한 테스트와 명시한 최소 인터페이스의 선언·미구현 stub으로 한정한다. 실제 업무 동작은 구현하지 않는다.

대상 테스트를 실행하고, 수집·실행된 테스트가 합의한 동작의 미구현이나 재현하려는 버그 때문에 실패하는지 확인한다.
종료 코드만으로 판정하지 않는다. 수집·문법·환경·fixture 오류, 테스트 미수집, skip·xfail은 유효한 Red가 아니다.
이러한 문제가 있으면 원인을 바로잡거나 상태를 보고하고, 유효한 실패를 확인하기 전에는 Green으로 넘어가지 않는다.

처음부터 통과하면 기존 동작과 테스트의 유효성을 조사하고 검증 목표를 다시 합의한다.
이미 충족된 요구사항이면 그 근거를 보고하며, 제품 코드를 고의로 깨뜨리거나 의미 없는 테스트를 추가해 Red를 만들지 않는다.

작성한 Given–When–Then, 실행 명령·종료 코드, 기대한 실패와 실제 실패 원인을 보고한다.
Green에서 반영할 최소 구현과 영향을 설명한 뒤 **Green 승인을 기다린다**. Red 완료는 전체 검증 통과를 뜻하지 않는다.

## Green: 최소 제품 코드 구현

**Green 승인을 받은 뒤** 해당 테스트를 통과시키는 최소 제품 코드를 수정한다.
대상 테스트와 영향 범위의 테스트를 실행해 새 동작과 기존 계약을 함께 확인한다.

기대값을 완화하거나 테스트를 제거·비활성화해 통과시키지 않는다.
테스트 변경이 필요하면 이유와 영향을 설명하고 Red로 돌아가 **다시 Red 승인**을 받는다.
승인된 구현 범위 안의 실패 수정과 재검증은 Green 안에서 처리한다.

변경 내용·검증 결과·남은 문제와 리팩터링 필요 여부를 보고한다.
개선이 필요하면 구체적인 변경과 영향을 설명하고 **Refactor 승인을 기다린다**.
리팩터링이 불필요하면 이유를 보고하고 생략한 뒤 공통 검증으로 사이클을 마무리한다.

## Refactor: 동작을 유지하는 구조 개선

**Refactor 승인을 받은 뒤** 외부 동작과 테스트의 검증 의미를 유지하며 코드·테스트 구조를 개선한다.
필요한 개선만 수행하고, 범위나 동작·기대값이 달라지면 현재 승인을 확대 해석하지 말고 다시 합의한다.
관련 테스트와 공통 검증을 실행하고 결과를 보고한 뒤 사이클을 종료한다.
다음 동작은 별도의 Red 설명과 승인부터 시작한다.

동작 유지 리팩터링만 요청한 경우에는 기존 테스트로 동작을 먼저 확인한다.
검증이 부족해 기존 동작을 확인하는 테스트를 추가해야 하면 그 필요성과 작성 범위를 승인받고, 현재 구현에서 통과하는지 확인한다.
이후 Refactor 승인을 받아 진행하며, 인위적인 Red나 불필요한 Green 구현 단계를 만들지 않는다.

## 검증과 결과 보고

- Red는 대상 테스트의 의도한 실패로 판정한다. 전체 공통 검증은 수정 전 기준 확인과 사이클 종료에 실행한다.
- 단위 테스트와 기존 mock·TestClient·SQLite 방식을 우선 활용한다. PostgreSQL 고유 동작은 별도 통합 검증 필요 여부를 계획에 명시하고 SQLite 결과로 대체 검증을 주장하지 않는다.
- 보고에는 현재 단계와 승인 범위, 변경 내용, 실행 명령·대상·종료 코드, 기대 결과와 실제 결과, 남은 문제, 다음 승인 대상을 포함한다. 기록은 대화와 인계에 남긴다.
- 사이클 종료 시 `uv run python scripts/check.py`가 통과해야 전체 검증 통과로 보고한다. 기존 실패가 남았거나 검사를 실행하지 못했으면 그 사실을 명시한다.
- 승인을 기다릴 때는 [작업 시작 스킬](../start-task-workflow/SKILL.md)의 안내에 따라 해당 승인 규칙을 이름·경로와 함께 인용한다. 실행하지 못한 도구·운영체제·대화 동작은 미검증으로 기록한다.

이 스킬은 승인 절차와 검증 판단을 안내한다. 자동 실행기·훅·CI·역할 분리는 도입하지 않으며 커밋·push·DB 적용 권한을 추가하지 않는다.
