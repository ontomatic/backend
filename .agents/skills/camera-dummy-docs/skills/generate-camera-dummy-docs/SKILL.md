# 카메라 더미 문서 생성

아래 `scripts/` 경로는 이 파일이 있는 스킬 폴더를 기준으로 한다. 저장소 루트에서는 `skills/generate-camera-dummy-docs/scripts/`를 사용한다. 문서 생성은 에이전트가 환경의 파일 제작 스킬과 도구로 수행하며, 포함된 Python 도구는 입력 목록 작성·구조 검증·자동 채점을 담당한다.

## 참고 자료

- 수량·문서군·폴더를 정할 때 [프로젝트 구성](references/project-recipe.md)을 읽는다.
- 골드와 변형을 만들기 전에 [데이터 계약](references/data-contract.md)을 읽는다.
- 레이아웃과 업무 이력을 만들 때 [부서별 양식](references/realistic-forms.md)을 읽는다.
- 재사용 요청문은 [실행 프롬프트](references/prompts.md)를 사용한다.

## 원칙

1. 첨부 PDF를 실제로 읽고 출처 파일명·페이지·짧은 근거·SHA256을 기록한다. 원본에 없는 정보를 원본의 사실로 표현하지 않는다.
2. 제품 유형과 항목 구조를 참고하되 가상 제조사·제품명·모델명·제품코드·핵심 사양을 재설계한다. 확장자 변경이나 원본의 이름만 바꾼 것을 기본 제품이라고 부르지 않는다.
3. 제품 기준 골드 → 문서별 기재 데이터와 변형 명세 → 4가지 형식 순서로 생성한다. 형식마다 값을 따로 만들지 않는다.
4. 문서번호·개정·담당·검토·판정·후속 조치로 현실감을 구현한다. 불합격→재시험→이관 보류, 자재 부족→보충 후 착수를 날짜와 이유로 연결한다.
5. 가상 제품·담당자·공급처·인증 번호를 실제 기업의 사실이나 공식 증빙으로 제시하지 않는다. 교육용 합성자료 표시를 읽기 쉬운 위치에 넣는다.
6. 문서에 없는 항목은 추출 골드에서 null로 둔다. 제품 기준값으로 채우지 않는다. 문서 추출 정답과 기준값 충돌 정답을 별도로 보존한다.
7. 영상 해상도와 센서 유효화소, 질량 g와 가속도 g0, IP와 IK를 구분한다. 서로 다른 의미를 무조건 별칭으로 묶지 않는다.
8. 같은 제품군의 기본·변형·4형식을 같은 데이터 분할에 둔다. 골드를 파서·LLM 입력에 섞지 않는다.

## 1 입력 확인

`python scripts/inventory_sources.py INPUT.zip --output source_inventory.json`으로 ZIP 내부 파일 수와 해시를 확인한다. 이 스크립트는 내용을 판독하지 않으므로 PDF를 별도 추출·열람한다. ZIP 수와 내부 PDF 수를 혼동하지 않는다.

대화에서 합의된 범위를 따른다. 17개 원본 프로젝트 재현은 기본 17개 + 중복 8개 + 유사 9개, 문서군 5종, 형식 4종으로 설정한다. 다른 입력에 이 수량을 강제하지 않는다. 기준 제품 20개가 필요하면 추가 합성 기준 제품 3개를 구분한다.

## 2 골드와 문서 모델 작성

제품마다 product_id, identity_id, family_id, source_id, variant_type, class_path, attributes를 만든다. 출처와 합성 필드의 생성 이력을 연결하고 실제 변경한 핵심 속성을 기록한다.

중복본은 같은 identity와 기술 사양을 유지하면서 표시명·모델·유통 코드만 바꾼다. 유사본은 같은 family의 다른 identity로 만들고 의미 있는 사양을 변경한다. 부품·펌웨어·시험 조건의 영향도 검토한다.

문서를 공통 모델로 먼저 작성한다. 각 필드에 key·label·raw value·unit·normalized value·section을 두고 누락·별칭·단위·충돌을 기록한다. BOM·업무 이력 등 원본에 없는 정보는 합성으로 추가한다.

## 3 부서별 문서 생성

PDF·Word·스프레드시트 생성에 해당하는 환경 스킬을 읽고 따른다. 이 스킬은 엔지니어링 내용과 평가 계약을 규정하며 각 형식의 제작·렌더링 규칙을 대체하지 않는다.

BOM은 부품당 한 행, 릴리스는 배포당 한 행, 시험은 검사당 한 행, 이관은 확인 항목당 한 행으로 작성한다. 긴 공통 속성표만 반복하지 않는다. 제품 유형별 사용 목적과 자연스러운 검토 문장을 넣는다.

동일 문서의 4형식에 같은 값과 의도된 변형을 반영한다. XLSX 숫자·날짜는 실제 숫자·날짜 셀로 저장한다. CSV는 UTF-8 BOM의 일관된 내보내기 스키마를 사용한다. HWPX는 요청과 생성 역량이 확인될 때만 추가하고 다른 형식의 확장자를 바꿔 제공하지 않는다.

## 4 정답 위치와 폴더 확정

최종 레이아웃에서 PDF 실제 페이지·인용·XLSX 셀·CSV 행을 기록한다. 문서 편집 후 이전 위치를 그대로 두지 않는다. Word 페이지의 렌더러 의존성을 명시한다. 값 셀만 인용하면 항목명과 섹션을 함께 보존한다. 표 직렬화 문자열을 실제 연속 원문으로 주장하지 않는다.

기본 제품 / 중복·유사 변형 / 정답·평가자료를 분리한다. 변형 아래에서도 중복과 유사를 나눈다. 제품 유형 → 문서 종류 → 형식별 파일 순서로 정리한다. 경로 변경 시 manifest와 채점 코드의 상대 경로를 갱신한다.

쌍 라벨의 duplicate/similar/unrelated 정의와 클래스별 수량을 공개한다. unrelated가 제품군 기준인지 일반적 의미인지 명시한다. 전체 정확도와 macro F1을 함께 보고한다.

## 5 검증과 전달

`python scripts/validate_dataset.py DATASET_ROOT`로 구조·참조·형식·골드 계약을 검사한다. 이 검사는 실제 파서 정확도나 시각적 품질을 증명하지 않는다. 별도로 다음을 확인한다.

- 전 형식의 실제 값·단위·누락·변형을 골드와 대조한다.
- BOM과 생산 자재번호·수량, 계획 수량과 소요량, 재고와 수급 판정, 품질 판정과 이관 상태를 대조한다.
- PDF·DOCX·XLSX를 렌더링하여 한글·표 폭·줄바꿈·잘림·페이지를 확인한다. 결재란만 마지막 페이지에 남지 않게 수정한다.
- 정답 예측, 빈 예측, 잘못된 값·단위·환각·충돌 누락을 넣은 예측으로 채점 코드를 검증한다.
- ZIP 파일 수·CRC·상대 경로를 검사하고 SHA256 목록을 만든다.

`python scripts/score.py --dataset-root DATASET_ROOT predictions.json`으로 전체 문서 필드·분류·쌍·충돌을 채점한다. 제품 사양만의 점수가 필요하면 scope별 집계를 추가한다. oracle 점수는 자체 점검이며 실제 모델 성능이 아니다. 인용·위치 정확도는 별도 평가한다.

환경의 파일 저장 절차에 따라 ZIP을 저장하고 실제 다운로드 링크를 제공한다. 기본/변형 수, 5문서군×4형식의 파일 수, 정답 포함 여부를 짧게 알린다. GitHub 업로드는 사용자가 요청한 경우에만 지정된 저장소·경로에 수행한다. 원본 PDF·개인정보·인증 정보·불필요한 생성 파일을 스킬과 함께 올리지 않는다.
