# 신규 작업 시작과 단계별 반영

새 변경 작업은 **main 최신화 → 상세 문답과 계획 → 작업 브랜치 생성 → 단계별 이해 확인과 반영** 순서로 진행한다.
공통 작업 규칙은 [rules.md](../../rules.md), 검증·리뷰·DB·커밋 절차는 [workflows.md](../../workflows.md)를 따른다.
아래 경로와 명령은 저장소 루트를 기준으로 한다.

## 적용 시점과 모드

- 새 기능·버그 수정·리팩터링·문서·설정 변경을 시작할 때 적용한다. 기존 작업을 이어가는지 불분명하면 먼저 확인한다.
- 같은 작업의 후속 질문·수정·리뷰·커밋은 현재 브랜치와 진행 상태에서 이어간다. main 최신화나 새 브랜치 생성을 반복하지 않는다.
- 여기서 계획 모드는 구현 전에 조사·질문·설명하는 절차이다. 승인 전에는 Git 준비에 필요한 fetch·main의 fast-forward·작업 브랜치 생성과 전환만 허용하며, 코드·테스트·설정·문서를 새로 작성하거나 수정하지 않는다. 읽기 전용 조사·검사에 필요한 캐시는 구현 변경으로 취급하지 않는다.
- 앱의 실제 Plan 모드나 실행 정책이 Git 변경을 금지하면 읽기 전용 점검까지만 수행하고 필요한 모드 전환을 안내한다. 도구로 앱 모드를 자동 전환하거나 실행 제한을 우회하지 않는다.
- 이 스킬과 공통 진입 지침이 main에 반영된 뒤 신규 작업에 사용한다. 도입을 위해 자동 merge·push를 수행하지 않는다.

## 1. Git 사전 점검과 main 최신화

작업 내용을 구현하기 전에 저장소와 현재 Git 상태부터 확인한다.

```text
git status --porcelain=v1
git branch --show-current
git worktree list --porcelain
```

- 미커밋 변경에는 추적 중인 파일의 변경과 미추적 파일을 포함한다. 변경이 있으면 내용을 알리고 처리 방법을 질문한 뒤 중단한다. 자동 stash·커밋·폐기는 하지 않는다.
- 현재 브랜치, `origin`, 로컬 main을 확인할 수 없거나 다른 worktree에서 main을 사용 중이면 상태를 설명하고 중단한다. 다른 worktree를 변경하지 않는다.

사전 점검이 끝나면 원격 main을 가져온다. 실패하면 최신화됐다고 보고하거나 다음 절차를 진행하지 않는다.

```text
git fetch origin main
git rev-list --left-right --count main...origin/main
```

마지막 명령의 왼쪽 숫자는 로컬 main에만 있는 커밋 수이다. 이 값이 `0`일 때만 계속한다.
로컬 main에 추가 커밋이 있거나 이력이 분기했으면 상태를 설명하고 중단한다. 강제 reset이나 자동 rebase로 해결하지 않는다.

```text
git switch main
git merge --ff-only origin/main
git rev-parse HEAD
git rev-parse refs/remotes/origin/main
```

각 명령의 성공을 확인하고 두 커밋 해시가 같은지 확인한다. 다르면 중단한다.
최신화한 main의 기준 커밋을 기록해 사용자에게 알린 뒤 요구사항 확인으로 넘어간다.
기존 작업 브랜치의 커밋을 main이나 새 작업에 자동 병합하지 않는다.

## 2. 상세 질문과 계획 합의

최신 코드와 테스트에서 확인할 수 있는 사실은 직접 조사한다. 사용자의 의도와 선택이 필요한 부분을 상세히 질문하고 답변을 반영한다.

- 작업 목적과 현재 문제, 원하는 동작과 사용자가 기대하는 결과.
- 포함할 변경과 제외할 변경, 제약과 호환성, 중요한 실패·경계 사례.
- 성공 기준, 검증 방법, 선택 가능한 접근 방식의 차이와 영향.

답을 받아도 중요한 불확실성이 남으면 후속 질문을 한다. 사용자가 이미 결정한 내용을 반복해서 묻지 않는다.
구현은 검증 가능한 단계로 나누고 각 단계의 변경 대상·동작·영향·완료 기준을 설명한다. 고정된 단계 수를 강요하지 않는다.
계획은 먼저 대화에서 설명한다. 질문·계획 작성이나 단순 이해 확인을 구현 파일 수정의 허가로 간주하지 않는다.

## 3. 작업 브랜치 생성과 전환

작업 내용과 단계가 정리되면 작업 유형과 짧은 영문 kebab-case 작업명을 조합해 생성할 브랜치 이름을 알린다.
접두사는 `feat/`, `fix/`, `refactor/`, `docs/`, `test/`, `chore/` 중 변경 목적에 맞게 선택한다.

- `git check-ref-format --branch`로 이름을 확인하고 로컬에 같은 이름이 없는지 확인한다. 원격은 캐시된 브랜치 목록만으로 판단하지 말고 `git ls-remote --exit-code origin "refs/heads/<유형>/<작업명>"`으로 확인한다. 종료 코드 `0`은 이름 충돌, `2`는 일치하는 브랜치 없음이며 그 외 오류는 중단한다. 이름이 겹치면 사용자에게 확인하고 중단한다. 기존 브랜치를 재사용·덮어쓰기·삭제하지 않는다.
- main이 1단계에서 기록한 기준 커밋과 같은지 확인한다. 달라졌다면 main 준비를 다시 확인하고 계획에 미치는 영향을 사용자에게 설명한다.
- 브랜치 생성 직전에 작업 트리가 여전히 깨끗한지 확인한다. 새 미커밋 변경이 있으면 처리 방법을 확인할 때까지 중단한다.
- 최신화한 main에서 `git switch -c "<유형>/<작업명>" main`으로 새 브랜치를 생성하고 전환한다.
- 현재 브랜치 이름과 HEAD가 의도한 이름·기준 커밋인지 확인한다. Git 명령이 실패하거나 확인 결과가 다르면 중단하고 상태를 알린다.

브랜치 생성은 Git 준비 절차이다. 브랜치를 만들었다고 구현 승인이 생기는 것은 아니다.

## 4. 단계별 이해 확인과 반영

각 구현 단계마다 다음 순서를 지킨다.

1. 지금 반영할 단계의 변경 대상·동작, 사용자에게 미치는 영향, 검증과 완료 기준을 구체적으로 설명한다.
2. 사용자가 내용을 이해했는지 확인하고 **해당 단계의 반영을 승인하는 명확한 응답**을 기다린다. 설명 요청이나 다음 단계에 대한 논의를 승인으로 간주하지 않는다. 응답이 애매하면 확인한다.
3. 승인된 단계 안에서만 코드·테스트·설정·문서를 변경한다. 같은 범위의 실패 수정과 재검증은 해당 단계 안에서 처리한다. 범위나 접근 방식이 달라지면 설명하고 다시 확인받는다.
4. 필요한 검사와 공통 검증을 실행하고 변경 내용·검증 결과·남은 문제를 보고한다. 다음 단계의 변경과 영향을 설명한 뒤 **새 승인을 기다린다**. 현재 단계의 승인을 다음 단계에 자동 적용하지 않는다.

승인을 기다릴 때는 미완료 단계와 확인이 필요한 이유를 알리고, 이 스킬의 해당 단계별 승인 규칙을 이름·경로와 함께 인용한다.
수정하지 않은 파일이나 실행하지 못한 검증을 완료했다고 보고하지 않는다.

## 완료와 인계

마지막 단계가 끝나면 전체 변경, 검증 결과, 남은 문제를 정리한다. 커밋 메시지 형식과 실행·DB 명령은 [README.md](../../../README.md)를 기준으로 한다.
이 스킬은 커밋·push·DB 적용 권한을 추가하지 않는다. 해당 작업은 기존 지침과 사용자의 요청 범위 안에서만 수행한다.
후속 요청에서는 완료한 단계, 승인 범위, 현재 브랜치를 확인해 이어가며 새 작업의 시작 절차를 다시 적용하지 않는다.
