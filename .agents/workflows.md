# 작업별 절차

작업 시작 시 [rules.md](rules.md)를 읽고, 아래에서 해당 작업의 절차를 확인한다.
설치·실행·DB 명령과 커밋 형식의 기준 문서는 [README.md](../README.md)이다.

## 환경 준비와 앱 실행

README의 `1. Getting Started`와 `2. Run`을 따른다.
별도 표시가 없는 명령은 Windows PowerShell·Git Bash와 macOS zsh에서 동일하며, 저장소 루트에서 실행한다.
기존 `.env`와 개인 설정을 보존하고, 필요한 경우 README의 의존성 동기화 절차로 환경을 준비한다.

## 구현

새 변경 작업은 [start-task-workflow](skills/start-task-workflow/SKILL.md)의 Git 준비·요구사항 문답·브랜치 생성·단계별 승인 절차를 따른다.
동작 유지 리팩터링은 기존 테스트로 동작을 확인한 뒤 필요한 개선을 승인받는다.
필요한 테스트만 작성하며, 기존 테스트를 형식 통일 목적으로 일괄 수정하지 않는다.
승인된 단계 안에서 필요한 코드와 회귀 테스트를 수정하고 단계에 맞는 검증을 수행한다. UI·API·DB·저장소 동작이 바뀌면 해당 동작도 추가로 확인한다.
단계별 변경 내용·검증 결과·남은 문제를 보고한 뒤 다음 단계의 승인을 기다린다. 실행하지 못한 검사는 미검증으로 명시한다.
같은 작업의 후속 요청은 현재 브랜치와 승인 상태에서 이어가며 시작 절차를 반복하지 않는다.

## 리뷰

변경 diff와 관련 코드를 읽고 동작·반환 계약·경계 사례·회귀 위험을 확인한다.
문제가 있으면 위치, 발생 조건, 영향, 근거를 함께 보고하고 검증 여부를 구분한다.
리뷰 요청의 범위를 지키며, 발견한 문제와 실제 수정한 내용을 구분해 기록한다.

## DB 변경

README의 `3. Manage Database Migration`을 따른다.
모델과 migration의 관계, 새 모델의 metadata 등록, 생성한 `upgrade()`·`downgrade()`·`down_revision`을 검토한다.
공유·배포된 revision의 이력은 유지하고, 모델과 관련 migration을 함께 관리한다.
적용 및 되돌리기 검증은 README에 명시한 DB 범위에서 수행하고 결과를 기록한다.

현재 Ruff 설정은 migration 디렉터리를 검사에서 제외한다. 공통 검증은 DB 변경을 적용하지 않으므로 migration은 별도로 검증한다.

## 커밋

커밋을 요청받으면 README의 `6. Commit Msg`에 있는 형식을 따른다.
목적이 같은 변경을 묶고 필요한 파일만 스테이징한 뒤 staged diff와 검증 결과를 확인한다.
커밋 메시지가 실제 변경과 일치하는지 확인하고, 비밀값·캐시·실행 로그가 포함되지 않도록 한다.
DB 변경을 포함하면 적용·되돌리기 검증 여부도 본문에 기록한다.

## 공통 검증

기존 진입점은 그대로 사용한다.

```text
uv run python scripts/check.py
```

검증기는 자신의 위치에서 저장소 루트를 계산하고, 같은 Python 인터프리터로 Ruff 코드 검사 → 포맷 확인 → backend pytest를 실행한다.
앞선 검사가 실패해도 나머지 검사를 시도하며 각 검사 출력과 최종 결과를 보여준다.
모두 성공하면 종료 코드 `0`, 검사 실패나 실행 오류가 있으면 `1`을 반환한다.
검증기 자체는 파일 자동 수정이나 의존성 설치를 수행하지 않는다.

작업 완료 전에 공통 검증과 변경 내용에 필요한 추가 검증을 수행한다. 기존 실패가 남았거나 검사를 실행하지 못했으면 결과에 명시한다.

## 결과 보고와 인계

두 도구 모두 구현·리뷰를 수행할 수 있다. 결과 보고와 도구 간 인계에는 **작업 목표, 변경 내용, 검증 결과, 남은 문제**를 포함한다.
검증 결과에는 실제 실행한 명령과 결과를 적고, 실행하지 못한 검사·운영체제·도구는 미검증으로 명시한다.
